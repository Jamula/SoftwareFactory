# Protected squash simulation

`tools/engineering-factory/protected-squash.mjs` and `tools/engineering-factory/pull-signals.mjs` evaluate protected squash eligibility and serialized shadow integration using either synthetic fixtures or bounded, read-only GitHub REST API metadata (`GET` only, `redirect: 'error'`, 5-second `AbortSignal.timeout`, 512 KiB stream byte cap, pagination fail-closed, and no untrusted body leakage). Every result keeps `shadow: true` and `liveMerge: false`. A native merge-queue rule stops this path (`QUEUE_PATH_REQUIRED`), including when queue status cannot be established.

An intent names the repository, immutable repository ID, protected branch, PR number, candidate head, and expected base. `DEFAULT_FACTORY_SCOPE` defaults to `Jamula/SoftwareFactory` (`1471342715`, `main`, and `['build-test', 'upload-coverage-javascript', 'windows-aspire-runtime', 'CodeQL']`), while `guardedSquashEvidence`, `platformMergeGates`, `readPullSignals`, `readProtectedSquashCandidate`, `createGitHubShadowTransport`, and `createShadowSquashController` accept explicit trusted scope and policy inputs for enrolled consumer repositories without weakening SoftwareFactory's 98% line / 95% branch coverage or consumer >=95% line / >=90% branch (or stricter policy) gates.

For `Jamula/SoftwareFactory`, when GitHub's native `pull_request` ruleset sets `required_approving_review_count: 0` because Copilot Pull Request Reviewer emits `COMMENTED` reviews, `readProtectedSquashCandidate` records `requiredApprovingReviewCount: 0` truthfully and enforces the hosted exact-head independent review gate through `classifyReviewSummary`, `buildCandidateReviewEvidence`, `normalizeReviewHistory`, and `planReviewBatch`. Consumer repositories still require native `required_approving_review_count >= 1` and formal `APPROVED` reviews. Stale heads, dismissed or `CHANGES_REQUESTED` reviews, summary-only unresolved findings (even when inline threads are resolved), self-authored or agent-authored reviews, mid-read head/base races, and failing pre-merge `main` checks all fail closed before simulation.

`createShadowSquashController` serializes on one instance and re-reads fresh candidate evidence before handing frozen identifiers to the simulated squash callback. An ambiguous receipt or failing post-merge `main` check holds the controller in recovery (`MAIN_VERIFICATION_REQUIRED` / `RECOVERY_REQUIRED`) with `dependentWorkAllowed: false`. Recovery reconciles the existing candidate receipt and `readBranchHealth` without repeating simulation; the next candidate must target the verified `mergeCommit` (`BASE_MOVED_SINCE_VERIFICATION`). Nothing performs a live GitHub merge, rolls back `main`, clears an uncertain receipt, or synthesizes an approval.

Run the tests and coverage gate with `npm ci --ignore-scripts && npm run test:coverage`. Durable cross-process lease/receipt persistence, live GitHub mutation authorization, and live merge-queue enrollment remain separate gates in #8.
